# ADR-0009: Item files: plan.md in the branch, criteria.json never committed

- Status: accepted
- Date: 2026-11-23

## Context

An item's work must survive context resets, machine failures and hand-overs, but the item's scaffolding must not pollute main, and the acceptance criteria must not be rewritable by the agent being judged by them.

## Decision

- **`plan.md`** is written by the implementer at the worktree root in the plan step (files, steps, risks, how each criterion will be verified). It is committed and pushed with every step on the item branch (`br/<item>-<slug>`), so whoever resumes the item has it. It is the item's memory after compaction and is reinjected by the `prime` hook. At a squash integration it is **stripped** from the tree that lands on main.
- **`criteria.json`** is regenerated by the daemon from the event log for the agent to read. It is excluded from git in the worktree, never committed, and the policy denies agent writes to it. The agent marks criteria only through a delivery, with evidence; only analysts and the owner rewrite criteria (`barnraise item edit`).

## Consequences

- Reviewers see plan and criteria as the item's memory, not as part of the change's scope.
- Main stays clean; the branch keeps the full story until it is deleted.
- With `merge.mode: steps` the step commits land as they are, so `plan.md` handling only applies to squash.
