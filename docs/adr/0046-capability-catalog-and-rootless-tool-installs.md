# ADR-0046: A native capability catalog, and pinned, checksum-verified, rootless tool installs

Status: accepted

## Context

Barnraise grew many features whose working depends on the machine: Landlock needs a kernel ABI, bubblewrap needs unprivileged user namespaces (which AppArmor refuses on recent Ubuntu), the microVM needs smolvm, `/dev/kvm` access and an image, build caches need a filesystem that clones files, the egress broker needs the proxy and its CA, and a handful of features use an optional program when it is installed (mergiraf, rtk, osv-scanner, ast-grep, gitleaks, Tailscale) and fall back to something weaker when it is not. Each feature logged its own line at start, in its own words, on its own machine. An owner with three machines could not tell what was on, what would work if switched on, what ran on a fallback and why, nor what to do about it. `barnraise up` checked only git push access, tokens and the programs of checks and plugins.

Installing the optional tools was left to the owner, with instructions that differ per tool and per system (cargo, npm, a release archive with bundled libraries for smolvm).

## Decision

1. **A native catalog.** `internal/domain/capability_catalog.go` declares every such feature as a capability: id, title, group, kind (native, optional, plugin), its requirements (a program with a minimum version, the Landlock ABI, bubblewrap usable, `/dev/kvm` accessible, copy-on-write clones on the data folder, the egress CA, a provider login, docker compose, a `daemon.yaml` setting), the switch that turns it on (a `barnraise.yaml` key, `daemon.yaml`, the daemon's `--egress`), what runs instead while a requirement is missing, and the fix. Plugins and ACP agents of the configuration add one entry each. A pure function evaluates a probe of the machine and the projects' configuration into one status per capability: `active`, `available` (all it needs is here, switched off), `degraded` (on, running on a fallback), `missing` (cannot run here) or `unsupported` (not for this system), with a one-sentence reason and the fix.
2. **A probe behind a port.** `ports.CapabilityProber` (adapter `internal/adapters/out/capprobe`) finds the programs and their versions (each `--version` through the `Exec` port under a 5-second timeout, in parallel), the Landlock ABI (the Landlock adapter's own probe), whether bubblewrap starts (the ACP adapter's probe), `/dev/kvm`, a real `FICLONE`/`clonefile` of a temporary file in the data folder (the reflink adapter), the egress CA file and the provider accounts. It caches the answer for five minutes and forgets it after an install.
3. **The cluster sees it.** Two additive RPCs, `Capabilities` and `InstallTools`, answer for the daemon's machine and are passed on to the requested peers over NATS, as standby and stop already are. They are owner and admin only, and absent from the session-token allow-list. `ListMachines` carries a count per status for each machine (`capability_counts`), refreshed every ten minutes and after an install, so a machines view can show a badge without asking every machine.
4. **Rootless, pinned, verified installs.** `barnraise tools install` installs mergiraf, rtk, osv-scanner, ast-grep and smolvm where upstream ships a build (Linux amd64/arm64, macOS arm64/amd64; smolvm has no macOS amd64 build). Each recipe (`internal/domain/toolrecipe.go`) pins a version, the official release asset per system and its sha256 written in the code: computed from the downloaded asset and compared with the upstream checksum file where the release has one (rtk, osv-scanner, smolvm) or with the digest GitHub shows for the asset (ast-grep); mergiraf's Codeberg release publishes none. The daemon downloads over HTTPS only, straight (the agents' egress proxy is not used, and redirects must stay HTTPS), checks the digest before anything is unpacked, and unpacks with no absolute or parent paths, no hard links or devices, no write through a symbolic link, links that stay inside the tool's folder (absolute links are kept only inside smolvm's guest root file system, where they name guest paths), setuid bits dropped, and limits on bytes and entries. The tool lands in `<data dir>/tools/<id>/<version>/`; its program is linked into `<data dir>/tools/bin/`. A newer pinned version replaces the old one, which is removed; `barnraise tools remove` removes only what Barnraise installed.
5. **Where the tools are found.** `<data dir>/tools/bin` is put first on the PATH of the barnraise process itself, so every lookup and every program it starts (setup, checks, hooks, agent sessions, plugins) finds them. The data folder is denied to confined commands, so `<data dir>/tools` is given back read-only in Landlock rulesets, mounted read-only at the same path in microVMs, and bound read-only in the bubblewrap sandbox of ACP terminals.
6. **Nothing with root is automated.** Bubblewrap, the `kvm` group, Docker, AppArmor and kernel settings are shown as the exact command for the owner to run, marked `needs_root`. Barnraise never runs them.
7. **Events.** `machine.tool.installed` (also for an upgrade, with `previous`), `machine.tool.removed` and `machine.tool.failed` are written to every project of the machine.

## Consequences

- `barnraise capabilities [--machine NAME ...|--all] [--project P]` answers "what runs here, and why not" in one place, for every machine; with the daemon stopped it probes this machine itself. `barnraise up` names what is switched on but degraded or missing and points to it.
- The pinned digests are a maintenance duty: raising a version means downloading the new assets and pinning their digests again. A tampered or replaced asset is refused, not installed.
- The tools Barnraise installs are third-party software under their own licenses (mergiraf is GPL-3.0; rtk's engine is under the Business Source License 1.1); Barnraise downloads the official builds on the owner's request and runs them as separate programs, it does not vendor or link them.
- Agents never reach the RPCs; an install is an owner action, audited (`machine.tools.install`, `machine.tools.remove`) and recorded as events.
- Sessions inside a project container (`container.image`) keep the image's own toolchain; the host's tools are not mounted there.
